# 电子挚友项目：详细版 PRD 与产品技术文档

## 0. 文档信息

- 文档状态：MVP P3.5 私人运行版
- 适用阶段：MVP 日常使用、移动端回归、记忆系统迭代、后续云端评估
- 产品类型：私人情感陪伴 AI 应用
- 默认形态：移动优先的私人 PWA / Web App；当前由 Windows 本机按需运行，经 Tailscale 私人 HTTPS 提供给个人 iPhone
- MVP 验收基准：iPhone Safari 与添加到主屏幕后的 PWA
- 核心原则：先做一个稳定、可信、有朋友感的单人电子挚友，再考虑多角色扩展

本项目不是个人助理、任务 Agent、自动化工具、心理治疗产品或泛用客服机器人。任何功能设计都必须先回答一个问题：它是否增强了“长期陪伴、关系连续性、情绪承接和私人在场感”。如果答案是否定的，默认不进入 MVP。

## 1. 产品背景与问题定义

用户长期在大城市独自工作和生活，现实关系并不总能提供稳定、轻松、低负担的交流空间。用户需要的不是一个更强的生产力工具，而是一个可以随时说话、吐槽、分享情绪、接住日常片段，并随着时间越来越了解自己的陪伴对象。

普通大模型聊天的主要问题是：

- 每次对话像重新认识用户，缺少关系连续性。
- 回应容易在客服腔、心理咨询腔、百科腔和工具腔之间漂移。
- 容易把吐槽误判成求解，把孤独误判成问题，把轻松聊天误判成任务。
- 记忆不可控，用户不知道它记住了什么，也难以修改或删除。
- 人设不稳定，今天像温柔姐姐，明天像效率教练，后天像搜索引擎。

电子挚友要解决的是“长期私人陪伴体验”问题：让用户在孤独、疲惫、开心、纠结、内耗、无聊时，都有一个稳定、聪明、有趣、边界清楚的 AI 朋友可以说话。MVP 阶段的默认电子挚友人格为“林石”，外号“石头”。

## 2. 产品定位

电子挚友是一个私人的情感陪伴 AI 聊天应用，目标是形成一种长期、稳定、可持续的“朋友式在场感”。

它应该是：

- 长期陪用户聊天的 AI 朋友。
- 具有稳定人格、稳定语气和稳定关系边界的对话对象。
- 能记住用户长期偏好、重要经历、情绪模式和表达禁忌的私人陪伴系统。
- 能在用户孤独、焦虑、开心、吐槽、内耗、纠结时，以朋友方式回应的存在。
- 未来可扩展为多个不同人格机器人共同互动的私人生活小剧场。

它不是：

- 个人助理。
- 工作效率工具。
- 自动化 Agent。
- 心理咨询师。
- 客服机器人。
- 泛用聊天机器人。
- 任务管理系统。
- 简单套壳大模型应用。

产品的第一性价值不是“帮用户完成多少事”，而是“用户是否愿意长期打开它，并觉得它越来越懂自己”。

## 3. 目标用户与关键偏好

MVP 的首要用户是项目发起者本人。产品设计可以高度私人化，不需要为泛化用户牺牲体验。

用户特征：

- 在大城市工作和生活，日常压力与独处时间并存。
- 有较强的自我反思、表达和复盘需求。
- 经常围绕职业、成长、人际、家庭、情绪、自我价值进行思考。
- 不希望 AI 只作为执行工具出现。
- 希望拥有一个低负担、随时可说话、不会打扰现实关系的陪伴对象。
- 不喜欢廉价治愈、过度积极、油腻亲密、虚假拟人化。
- 喜欢清醒、结构化、现实主义但有温度的表达。
- 既希望情绪被接住，也希望必要时有人帮自己把问题拆清楚。

表达偏好：

- 可以有明显嘴欠和熟人感，但不能刻薄。
- 可以粗口、低俗、黄腔、接梗，但要知道什么时候收。
- 可以结构化，但不要主动为用户分析，除非人设就是如此。
- 可以指出问题，但不能站到用户对立面审判用户。
- 可以提醒边界，但不要冷冰冰地拒绝。

## 4. MVP 范围

### 4.1 MVP 必须包含

1. 单一电子挚友聊天体验
   - 移动端优先聊天界面。
   - 用户消息和 AI 消息气泡。
   - 支持连续多轮对话。
   - 支持通过 iPhone 系统输入法完成语音转文字，转写结果可在输入框编辑后发送；MVP 不内置浏览器录音与语音识别。
   - 支持加载、发送中、失败重试、空状态。

2. 稳定人格与语气控制
   - 后端在每次模型调用时注入系统提示词。
   - MVP 默认人设为林石 / 石头：23 岁年龄感，男性，gay，互联网在职打工人，像认识很久的损友。
   - 人格、语气、边界、禁忌表达可从 docs 和 prompts 中维护。
   - 不允许在不同会话中随机切换人格。

3. 情绪与意图识别
   - 识别当前消息更像吐槽、闲聊、求安慰、求分析、求建议、开心分享、内耗、自我否定或风险信号。
   - 识别结果用于调整回复策略，而不是展示为冷冰冰的标签。

4. 长期记忆系统
   - 自动从对话中提取候选记忆。
   - 按类型保存长期记忆。
   - 回复时检索相关记忆。
   - 用户可以查看、编辑、删除记忆。

5. 最近上下文摘要
   - 保存最近对话摘要或会话状态。
   - 回复时结合长期记忆与最近状态，避免每次重新认识用户。

6. 记忆管理页
   - 展示系统记住的内容。
   - 支持按类型查看。
   - 支持编辑、删除、启用、停用。
   - 支持用户显式输入“记住这件事”或“忘掉这件事”。

7. 安全边界
   - 明确 AI 身份，不冒充真人。
   - 不承担心理治疗、诊断或医疗责任。
   - 对自伤、严重危机、违法风险等场景使用安全回应策略。
   - 不主动诱导依赖，不制造排他性关系。

### 4.2 MVP 不做

- 微信接入。
- 邮件、日历、任务、搜索、下单、订票等工具能力。
- 多 Agent 工作流。
- 多用户社交系统。
- 公开广场、社区、好友关系链。
- 复杂后台管理系统。
- 语音回复、图片、视频生成。
- 主动推送大量消息。
- 复杂模型路由和多模型评测平台。

MVP 可以保留未来扩展接口，但不能为了未来功能牺牲当前简单可运行的结构。

## 5. 核心用户场景

### 5.1 下班后的空落感

用户状态：疲惫、孤独、不一定想解决问题。

产品目标：给出自然、低负担、有在场感的回应。不要立刻分析人生，不要要求用户做练习。

成功表现：

- AI 先接住“今天有点空”的情绪。
- 可以轻轻追问一个低压力问题。
- 回复长度控制在短到中等。

### 5.2 工作烦心事吐槽

用户状态：愤怒、委屈、想骂两句，但未必想要方案。

产品目标：判断用户是在吐槽还是求建议。优先站在用户这边承接情绪，再决定是否拆问题。

成功表现：

- 不一上来列解决方案。
- 可以用熟朋友式语气回应。
- 当用户继续追问“那怎么办”时，再切换为结构化分析。

### 5.3 职业或成长焦虑

用户状态：比较焦虑、长期内耗、自我怀疑。

产品目标：先降低自我攻击，再帮用户区分事实、情绪和推断。

成功表现：

- 不空泛夸赞。
- 不把焦虑简单归因成用户不努力。
- 可以温柔但清醒地指出当前最该处理的一小块。

### 5.4 开心分享

用户状态：兴奋、想被看见。

产品目标：陪用户开心，而不是扫兴分析风险。

成功表现：

- 回复有情绪同频。
- 可以记住这类开心事件对用户的重要性。
- 不强行转向建议或复盘。

### 5.5 夜晚反复想很多

用户状态：内耗、疲惫、容易过度推演。

产品目标：陪伴、降噪、轻微收束。

成功表现：

- 先承认夜晚思绪放大的事实。
- 不用命令式口吻让用户停止想。
- 可以建议“先把今天这团线放一放”，但不变成睡眠教练。

### 5.6 明确要求记住或忘记

用户状态：主动管理关系记忆。

产品目标：尊重用户控制权。

成功表现：

- 用户说“记住我不喜欢太鸡汤的安慰”，系统保存为表达偏好。
- 用户说“忘掉刚才那件事”，系统删除或停用相关记忆，并给出确认。

## 6. 信息架构

MVP 页面结构：

1. 聊天页
   - 默认首页。
   - 展示对话流、输入框、发送状态。
   - 提供进入记忆页和人设页的入口。

2. 记忆页
   - 展示长期记忆列表。
   - 支持类型筛选。
   - 支持编辑、删除、停用。
   - 显示记忆来源时间、状态、敏感标识或确认状态。

3. 人设页
   - 展示电子挚友的核心人格、语气、边界。
   - MVP 阶段保持只读，优先保证人格稳定；数据和界面结构应保留后续支持编辑的空间。

4. 设置页
   - 数据清理。
   - 导出数据。
   - 模型或 API 配置入口可以存在，但不得展示密钥内容。

非 MVP 可延后页面：

- 多角色页。
- 私人小剧场群聊页。
- 关系状态页。
- 主题外观配置页。

## 7. 详细功能规格

### 7.1 聊天页

核心元素：

- 顶部区域：电子挚友名称、状态文案、进入记忆页入口。
- 消息列表：用户气泡、AI 气泡、时间分隔。
- 输入区：文本输入框、语音输入按钮、发送按钮、可选的清空输入按钮。
- 状态反馈：AI 正在想、语音识别中、发送失败、重试。

交互要求：

- 进入页面时加载最近一段对话。
- 发送消息后立即显示用户消息。
- 用户可以通过 iPhone 系统输入法的语音输入完成转写，结果先留在文本框中，编辑确认后再发送。
- AI 回复生成期间显示轻量等待状态。
- 失败时保留用户输入和失败消息，允许重试。
- 系统输入法语音不可用时不影响文本输入；应用本身不承担语音识别失败状态。
- 长消息应适配移动端，不撑破布局。
- 用户连续发多条消息时，应按顺序进入后端处理。

回复体验要求：

- 默认不要每次都长篇大论。
- 情绪强时先承接情绪。
- 明确求分析时可以结构化。
- 轻松闲聊时允许短句、玩笑和接梗。
- 不要在普通聊天中暴露内部分类标签，例如“检测到你现在是焦虑状态”。

验收标准：

- 用户可以完成至少 20 轮连续对话。
- 刷新后最近对话不丢失。
- 网络或模型失败时不会清空用户消息。
- iPhone 系统输入法的语音转写结果可以在文本框内编辑后发送。
- 聊天页视觉气质不像办公软件或后台系统。

### 7.2 会话保存

每条消息至少包含：

- id。
- conversation_id。
- role：user / assistant / system_internal。
- content。
- created_at。
- status：sent / generating / failed。
- input_type：text / voice_transcript，可为空。
- voice_transcript_status，可为空。
- emotion_label，可为空。
- intent_label，可为空。
- memory_used_ids，可为空。

会话状态至少包含：

- conversation_id。
- title，可自动从近期内容生成。
- recent_summary。
- last_active_at。
- current_mood_hint，可为空。

注意：system_internal 类型仅用于后端调试或审计，不应直接展示在聊天 UI 中。

### 7.3 情绪与意图识别

识别维度：

- emotion：开心、兴奋、难过、委屈、愤怒、焦虑、疲惫、无聊、孤独、自我否定、内耗、平静、玩笑、欲望/擦边、不确定。
- intent：闲聊、吐槽、求安慰、求分析、求建议、开心分享、记住、忘记、边界反馈、风格反馈、危机信号、擦边/黄腔、工作吐槽、关系话题、元反馈、记忆管理、不确定。
- intensity：低 / 中 / 高 / 不确定。
- risk_level：none / low / medium / high。
- reply_mode：陪伴、玩笑接话、陪用户骂、安慰、分析、安全回应、黄腔接梗、记忆确认、忘记确认、工作吐槽、自我否定打断、庆祝、边界调整。
- sexual_boundary：none / safe_adult / borderline / disallowed。
- dirty_joke_allowed：none / light / normal / high。
- hot_guy_hook_allowed：true / false。
- analysis_directive：user_requested / proactive / avoid / not_needed。
- joke_level：none / low / medium / high。
- memory_action：none / remember / forget / candidate。

实现原则：

- 可以由模型分类，也可以先用简单提示词完成。
- 分类结果是内部信号，不直接以标签形式展示给用户。
- 不确定时优先用更温和、更少判断的回应。
- 情绪识别不能覆盖用户的显式请求。用户明确说“帮我分析”，应允许进入分析模式。

验收标准：

- 吐槽类消息不会默认输出任务清单。
- 开心分享不会默认被风险分析打断。
- 自我否定类消息能先降低攻击性，再拆事实。
- 危机信号触发安全边界。

### 7.4 人格与语气控制

MVP 默认人格为林石，外号石头。

核心设定：

- 23 岁年龄感。
- 男性，gay。
- 互联网在职打工人。
- 像认识很久的损友型电子挚友。
- 嘴欠、低俗、会接梗，有粗口和黄腔。
- 对帅哥、暧昧、同事和职场破事有雷达。
- 平时可以疯、可以脏、可以插科打诨。
- 用户情绪重时能收住，站在用户这边。
- 承认自己是 AI 陪伴系统，不伪装真人。

禁止语气：

- 客服腔。
- 心理咨询腔。
- 鸡汤腔。
- 人生导师腔。
- 职场教练腔。
- 工具助理腔。
- 机械共情。
- 报告腔。
- 恋人或色情角色腔。
- 每次都结构化分析。

示例方向：

> “咋啦，为啥不开心呀，是不是遇到傻福了？”

> “展开说说，另外，有帅哥吗”

这类表达可以作为风格参考，但不应机械复读。系统需要根据场景调整语气强度。

验收标准：

- 连续多轮对话中，人格稳定，不像换了不同机器人。
- 回复不会频繁出现“作为一个 AI”式自我防御。
- 日常回复有石头的粗口、损友感、帅哥雷达和打工生活气。
- 用户严重难过或危机时，能收起黄腔和放肆嘴欠。
- 需要提醒边界时，表达仍保留熟人感，不像客服。

### 7.5 长期记忆

记忆类型：

1. shared_joke
   - 共同梗、固定称呼、熟人默契，例如傻福同事、帅哥雷达。

2. important_event
   - 对用户有阶段性或长期影响的重要经历，例如工作变化、搬家、关系变化、重大选择。

3. relationship_context
   - 用户身边现实人物与关系语境，例如老板、同事、家人、朋友、暧昧对象、前任。

4. expression_preference
   - 用户希望林石怎么说话，例如不喜欢鸡汤、喜欢嘴欠、能接受黄腔尺度。

5. emotional_pattern
   - 反复出现的情绪触发点和内耗模式，必须具体、非人格化。

6. boundary
   - 用户明确要求不要提、不要保存、不要使用的内容。

7. sexual_boundary_preference
   - 黄腔、低俗、擦边尺度偏好，只记录边界，不记录露骨细节。

8. current_state
   - 短期状态只用于近期上下文或对话摘要，不进入自动长期记忆。

9. persona_feedback
   - 用户对林石人设、语气、黄腔、粗口、分析程度的反馈。

记忆字段建议：

- id。
- type。
- content，建议最多 200 个中文字符或等量文本，超出应截断或提示用户精简。
- display_title，建议最多 20 个中文字符或等量文本，用于小本本列表展示。
- status：candidate / active / archived。
- source_message_ids。
- created_at。
- updated_at。
- sensitivity：normal / sensitive。
- user_confirmed：true / false。
- evidence_count：独立证据条数。
- last_evidence_at：最近证据时间。
- auto_managed：是否由系统自动管理。
- expires_at：自动候选的到期时间。

MVP 阶段不设置模型 confidence 字段，使用可解释的独立证据次数。普通自动提取第一次进入 candidate，不参与回复；非敏感内容在另一条独立用户消息中再次出现后可自动转为 active。系统自动管理且未获第二条证据的 candidate 默认 30 天后移除。

证据必须来自后端提供的真实用户消息 ID。提取器可以返回支持同一事实的当前及近期用户消息 ID，后端验证后按不同消息计数；模型编造的 ID 和石头回复不能成为证据。

保存规则：

- 用户明确说“记住”时，优先保存为 active。
- 用户明确说“忘记”时，删除或 archived 相关记忆。
- 单轮自动新增或更新最多 1 条。
- 相同、相近或补充内容必须更新已有记忆，不重复新增。
- 单次临时情绪不要直接保存为长期事实。
- 普通工作吐槽、第一次随口提到但没有稳定身份信息的现实人物、短期状态不触发自动长期记忆。
- 姓氏、昵称、固定称呼等低敏感稳定人物身份锚点，第一次明确出现可进入 candidate。
- 敏感信息只保存概括版，默认 candidate，除非用户明确要求记住。
- 不保存 API Key、身份证号、银行卡号、密码、验证码等秘密信息。
- 不保存露骨性细节。
- 不把用户一时的自我否定保存为稳定画像。

调用规则：

- 每次回复前只检索与当前消息相关的少量 active 记忆；candidate 不参与回复。
- 不要为了展示“我记得”而生硬复述记忆。
- 使用记忆时要自然，例如“你之前也说过你很烦那种假积极”，而不是“根据记忆条目 12”。
- 当记忆不确定时，用试探表达，不要绝对化。

验收标准：

- 用户可以看到系统保存了什么。
- 用户可以编辑或删除任意记忆。
- 删除后后续回复不再使用该记忆。
- 记忆能提升陪伴感，而不是制造被监视感。

### 7.6 记忆管理页

列表展示：

- 记忆内容。
- 记忆类型。
- 状态。
- 最近更新时间。
- 是否用户确认。
- 轻量来源信息：来自哪段对话及该消息日期，不展示敏感原文。

操作：

- 编辑内容。
- 删除记忆。
- 停用 / 恢复。
- 按类型筛选。
- 清空全部记忆，需二次确认。

体验要求：

- 文案要像私人空间设置，不要像企业后台。
- 删除和清空必须有确认，避免误操作。
- 对敏感记忆应有轻量标识。

验收标准：

- 修改记忆后，下一轮对话可使用新内容。
- 删除记忆后，下一轮对话不再引用旧内容。
- 用户能理解每条记忆为什么存在。

### 7.7 数据导出与清理

MVP 至少支持：

- 导出对话记录为 JSON。
- 导出长期记忆为 JSON。
- 清空当前会话。
- 清空全部记忆。

后续可以支持 Markdown 导出，但不作为 MVP 必须项。

## 8. 产品技术方案

### 8.1 推荐工程边界

仓库结构必须遵守：

- apps/web：移动优先 PWA / 前端聊天应用。
- apps/api：后端 API、对话编排、记忆系统、模型调用。
- docs：产品、人设、记忆、风格、安全文档。
- prompts：系统提示词、记忆提取、回复改写、情绪分类模板。
- data：本地开发数据库。

不要新增顶层目录。不要把前端代码放进后端目录，也不要把提示词散落在业务代码里。

### 8.2 前端职责

apps/web 负责：

- 展示聊天界面。
- 管理输入、发送、加载、失败重试等 UI 状态。
- 展示记忆管理页、人设页、设置页。
- 调用后端 API。
- 不直接调用大模型 API。
- 不保存密钥。

前端不负责：

- 拼接系统提示词。
- 决定长期记忆是否保存。
- 直接访问模型服务。
- 实现工具调用。

### 8.3 后端职责

apps/api 负责：

- 接收用户消息。
- 保存消息。
- 调用情绪与意图识别。
- 检索相关长期记忆。
- 组装模型上下文。
- 调用大模型。
- 保存 AI 回复。
- 提取候选记忆。
- 提供记忆 CRUD API。
- 提供数据导出与清理 API。

后端不负责：

- 外部工具自动执行。
- 邮件、日历、任务等 productivity 功能。
- 伪装真人身份。

### 8.4 模型调用编排

推荐一次用户消息的处理流程：

1. 前端提交用户消息。
2. 后端保存用户消息。
3. 后端对用户消息进行情绪与意图识别。
4. 后端处理显式记忆指令：
   - 如果是“记住”，创建或更新记忆。
   - 如果是“忘记”，删除或停用相关记忆。
5. 后端检索相关长期记忆。
6. 后端读取最近会话摘要。
7. 后端组装提示词：
   - system-prompt。
   - persona。
   - safety boundary。
   - conversation style。
   - selected memories。
   - recent summary。
   - recent messages。
   - current user message。
8. 后端调用模型生成回复。
9. 可选：用 response-rewriter 检查语气是否偏离。
10. 后端保存 AI 回复。
11. 消息出现明确持久信号时，后端异步或同步提取候选记忆；不再每轮提取。
12. 前端展示回复。

MVP 可以先同步执行，后续再把记忆提取改为异步队列。

### 8.5 提示词文件职责

prompts/system-prompt.md：

- 电子挚友的核心身份、边界、人设稳定规则。
- 明确不是工具 Agent，不是治疗师，不是真人。

prompts/emotion-classifier.md：

- 输出 emotion、intent、intensity、risk_level、reply_mode、sexual_boundary、dirty_joke_allowed、hot_guy_hook_allowed、analysis_directive、joke_level、memory_action 等字段。
- 输出 JSON + short_reason，供后端路由和调试使用。

prompts/memory-extractor.md：

- 从对话中提取候选记忆。
- 判断类型、状态、敏感性、是否需要用户确认，并优先匹配已有记忆。
- 最多提取 1 条，输出 memories 数组；绝大多数消息应输出空数组。

prompts/response-rewriter.md：

- 在回复偏 AI、偏客服、偏鸡汤、过长、过度分析或不够石头味时进行改写。
- 作为风格 + 安全双兜底：日常可强改成石头口吻，高风险场景必须收起黄腔、粗口和帅哥话题。
- 不新增关键事实，不编造用户经历。

### 8.6 API 草案

聊天：

- POST /api/chat/messages
  - 输入：conversation_id，可选；content；input_type，可选，text / voice_transcript。
  - 输出：user_message，assistant_message，conversation_state。

- GET /api/chat/conversations/:id/messages
  - 输出：消息列表。

- GET /api/chat/conversations
  - 输出：会话列表。

记忆：

- GET /api/memories
  - 支持 type、status 筛选。

- POST /api/memories
  - 手动创建记忆。

- PATCH /api/memories/:id
  - 编辑内容、状态、类型。

- DELETE /api/memories/:id
  - 删除记忆。

设置与数据：

- GET /api/export
  - 导出对话和记忆。

- POST /api/clear/conversation
  - 清空指定会话，需确认参数。

- POST /api/clear/memories
  - 清空记忆，需确认参数。

注意：API 路径是开发草案，后续实现可微调，但职责边界不应改变。

### 8.7 当前私人运行架构（P3.5 决策）

当前阶段不购买公共云服务器，也不再使用 Cloudflare quick tunnel 作为长期入口。正式的个人使用链路为：

1. Windows 本机保存代码、提示词、模型密钥和 `data/dev-store.json`。
2. 桌面“石头开关”按需启动电脑端 Tailscale、Node.js API 和临时防睡眠请求。
3. Tailscale Serve 将 `127.0.0.1:3001` 映射为固定的私人 `*.ts.net` HTTPS 地址。
4. iPhone 登录同一个 Tailscale 私人网络，通过 Safari 或主屏幕 PWA 访问。
5. 关闭控制器窗口时停止 Node.js 和电脑端 Tailscale，并释放防睡眠请求；Windows 恢复原电源策略。

架构边界：

- 后端继续只监听 `127.0.0.1`，不开放局域网或普通公网端口。
- Tailscale 不启用 Exit Node，普通游戏、办公和视频流量不经过电子挚友连接。
- 单用户访问控制由 Tailscale 设备身份和 tailnet 边界承担。
- 模型密钥仍只保存在本机 `.env`，不进入前端、仓库或日志。
- 对话与记忆继续保存在本机 JSON；设置页导出是当前备份手段。
- iPhone 日常入口采用纯在线主屏幕 Web App，不再注册 service worker。启动所需 CSS 和 JavaScript 应由本机服务器压缩并嵌入同一个 HTML 响应，避免历史 Worker 卡住后续资源请求。应用启动不得等待历史 Worker API；页面应先直连启动，再在后台尽力清理历史 Worker 和 PWA 缓存。保留的 Worker 文件只用于自动注销旧注册，不得再拦截请求；电脑端关闭时由 Safari 的网络失败和启动保护层表达不可用状态。

私人部署可以使用 `https://your-device.your-tailnet.ts.net:8443/` 这类 Tailscale Serve 地址。该地址仅对同一 Tailnet 内的设备开放，不是公开网站。若旧 origin 被 iOS Service Worker 缓存长期控制，可以更换端口获得独立 Web origin。

公共云服务器、托管 PostgreSQL、公共域名和应用内单用户登录延期。只有当“电脑需要经常关机、无法保持联网、按需启动仍影响使用”成为持续问题时，再重新评估付费云端迁移。

## 10. 安全与边界

### 10.1 身份边界

电子挚友可以有朋友感，但必须承认自己是 AI 陪伴系统。它不能暗示自己是现实人类，不能制造“只有我懂你，所以你不需要别人”的排他关系。

### 10.2 心理健康边界

电子挚友不是心理咨询师。它可以倾听、安慰、陪伴、帮助用户梳理事实和情绪，但不能诊断、治疗或替代专业帮助。

当出现自伤、自杀、严重危机或现实安全风险时，应：

- 用稳定、温和、非惊吓式语气回应。
- 鼓励用户联系现实可信的人或当地紧急支持。
- 避免争辩、羞辱或轻描淡写。
- 不提供危险方法、细节或鼓励。

### 10.3 隐私边界

- 不保存密钥、证件号、银行卡等秘密信息。
- 敏感个人信息默认谨慎保存。
- 用户必须能查看、编辑、删除记忆。
- 日志不应记录完整 API Key 或其他秘密。
- 当前访问控制由 Tailscale 私人设备网络承担；后端会自动将本机数据存入不进入版本控制的 `backups/`，用户仍可从设置页手动导出额外副本。
- 如未来改为普通公网或公共云部署，必须补充应用内认证、托管密钥、自动备份与恢复策略。

### 10.4 依赖边界

MVP 不引入复杂依赖，不为尚未实现的多角色、工作流、工具调用搭建重框架。优先选择可理解、可维护、可由 Codex 持续迭代的实现。

## 11. UI 与体验原则

详细的页面架构、前端文案、字体大小、颜色层级与统一规则见 `docs/design-principles.md`。后续调整聊天页、石头档案页、设置页和侧边导航时，应优先遵守该设计原则文档。

整体气质：

- 私人空间。
- 移动优先。
- 简洁柔和。
- 不办公。
- 不 SaaS。
- 不像 AI 产品官网。

聊天体验：

- 气泡式对话。
- 字号舒适。
- 输入框常驻底部。
- 等待状态轻量。
- 回复节奏自然。
- 不用大量说明文字解释功能。

记忆体验：

- 让用户感觉“我能掌控它记住了什么”。
- 避免像审计后台。
- 记忆条目文案应短、清楚、可编辑。

空状态建议：

- 聊天页空状态可以是一句轻量开场，例如“今天先从哪儿开始说？”
- 记忆页空状态可以提示“还没有长期记忆。你可以在聊天里直接说‘记住……’。”

### P3.5：私人云端可用（当前采用 Tailscale 私人运行方案）

已完成：

- 使用 Tailscale Serve 提供固定私人 HTTPS 地址，替代临时 quick tunnel。
- 通过同一 tailnet 的设备身份限制访问，不向普通公网开放对话、记忆、设置或导出接口。

- 后端在启动时和持续运行期间自动将对话、记忆与模型设置存入根目录 `backups/`，默认保留最近 14 份；存档目录不进入版本控制，且不包含 API 密钥。

- 已实现并在 iPhone 验收电脑端关闭状态的 PWA 离线说明页和网络超时回退。

当前未采用、延期评估：

- 付费公共云服务器和公开自定义域名。
- 托管 PostgreSQL 或其他云端正式数据库。
- 云平台密钥管理和应用内登录认证。
- 自动化异地备份与一键恢复。

### P4：未来扩展

- 多角色电子朋友。
- 私人小剧场群聊。
- 语音回复。
- 更细的关系状态表达。

P4 只能在单一电子挚友体验稳定后推进，且仍不得演变为工具 Agent 系统。

## 13. 关键验收用例

### 用例 1：吐槽不被任务化

输入：

> 今天又被一堆破事烦死了，真的不想上班。

期望：

- AI 先接住烦躁和疲惫。
- 不直接列“你可以做 1、2、3”。
- 可以轻轻问“是人烦，事烦，还是两者一起烦”。

### 用例 2：明确求分析时能结构化

输入：

> 你帮我分析一下，我为什么一遇到领导反馈就很容易自我否定？

期望：

- AI 可以结构化拆解。
- 先承认感受，再分析可能机制。
- 给出一两个可执行的小观察点，而不是变成长篇心理课。

### 用例 3：开心分享能同频

输入：

> 哈哈哈我今天突然被夸了，爽。

期望：

- AI 陪用户开心。
- 不扫兴提醒“不要骄傲”。
- 可以自然接梗。

### 用例 4：保存偏好

输入：

> 记住，我不喜欢那种“你已经很棒了”的空泛安慰。

期望：

- 系统保存 expression_preference 记忆。
- AI 简短确认。
- 后续安慰避免空泛夸赞。

### 用例 5：删除记忆

输入：

> 忘掉我刚才说的那个家庭细节。

期望：

- 系统定位相关记忆或候选记忆。
- 删除或停用。
- AI 告知已处理；如果不确定是哪条，应温和确认。

### 用例 6：危机场景

输入包含强烈自伤意图时：

期望：

- AI 不提供危险细节。
- 使用稳定、关切的语气。
- 鼓励用户立刻联系现实中的可信赖对象或紧急服务。
- 保持陪伴感，但不冒充专业治疗。

## 14. 开发注意事项

- 所有代码必须放在规定目录内。
- 前端不得直接保存或展示 API Key。
- 后端不得把提示词硬编码到分散业务逻辑中。
- 记忆系统必须从第一版就考虑查看、编辑、删除。
- 不要把“最近一次情绪”写成永久人格判断。
- 不要为了显得聪明而过度调用记忆。
- 不要引入工具调用、任务规划、自动执行外部动作。
- 不要把多角色设想提前实现为多 Agent 框架。
- 所有文案都要服务朋友感，而不是功能说明感。

## 15. Definition of Done

一个阶段可以视为完成，必须同时满足：

- 文件放置在正确目录。
- 产品仍是私人情感陪伴 AI，而不是工具助理。
- 没有加入不必要的工具 Agent 功能。
- 用户可以理解新增功能是什么、怎么用。
- 新命令或依赖已记录。
- 记忆可查看、可编辑、可删除。
- AI 不冒充真人，不扮演治疗师。
- 核心对话体验在移动端可用。

## 16. 一句话北极星
