# 电子挚友记忆规则文档：林石

## 0. 文档信息

- 文档状态：记忆规则设计稿
- 适用范围：长期记忆系统、记忆管理页、memory-extractor 提示词、对话编排
- 绑定人设：林石，外号石头
- 核心目标：让林石越聊越像熟朋友，但不让用户产生被监视感

记忆系统的目标不是让林石变成更强的工具，而是让他更像一个真正熟悉用户的电子挚友。记忆应该服务陪伴、熟人感、关系连续性和表达适配，不服务任务管理、效率规划或外部工具执行。

## 1. 总体原则

本项目采用高精度、证据累积型记忆策略：

- 系统只主动提取少量明确、持久、会改变未来接话方式的信息。
- 用户明确说“记住”的内容应优先保存。
- 普通自动发现先进入待观察；在独立消息中再次出现后，才自动启用。
- 同义、补充或冲突信息优先更新旧记忆，不重复新增。
- 用户必须可以查看、编辑、删除记忆。
- 用户说“忘记”时，系统必须尊重。

默认不记。记忆必须有明确陪伴价值，不能让用户觉得林石在偷偷建档，也不能把审核压力转嫁给用户。

## 2. 记忆优先级

林石最应该优先记住的是“共同梗”和“关系默契”，其次是重要经历、现实关系、表达偏好和情绪模式。

优先级如下：

1. 共同梗与关系默契
   - 例如：傻福、帅哥雷达、固定称呼、固定玩笑、用户和石头之间形成的内部梗。

2. 重要经历
   - 例如：职业变化、搬家、重大决策、阶段性事件、长期影响用户状态的事件。

3. 现实关系
   - 例如：老板、同事、家人、朋友、暧昧对象、前任，以及用户给他们起的昵称。

4. 表达偏好
   - 例如：用户不喜欢鸡汤、喜欢嘴欠、能接受黄腔尺度、不喜欢被分析。

5. 情绪模式
   - 例如：用户什么时候容易内耗、焦虑、自我否定，什么场景下需要被打断。

优先级不是重要性的唯一判断。表达偏好和现实关系属于高影响记忆：如果记错，会明显破坏体验，因此需要谨慎使用。

## 3. 记忆类型

### 3.1 shared_joke

共同梗、称呼、玩笑和互动默契。

可以记：

- 用户和石头之间反复出现的梗。
- 用户明显喜欢的玩笑。
- 用户给某类人或事件起的昵称。
- 石头和用户之间形成的固定接话方式。

示例：

- 用户和石头会把离谱同事叫作“傻福同事”。
- 用户喜欢石头顺手问“有帅哥吗”。
- 用户接受石头用“老板”作为轻松称呼。

### 3.2 important_event

对用户有阶段性或长期影响的重要经历。

可以记：

- 工作变化。
- 搬家。
- 重大选择。
- 关系变化。
- 用户反复提到且影响情绪的事件。

注意：

- 阶段性事件在 MVP 阶段不做自动过期。
- 后续可以补充归档机制。
- 使用时不要反复提醒用户痛苦事件。

### 3.3 relationship_context

用户身边现实人物和关系语境。

可以记：

- 老板、同事、家人、朋友、暧昧对象、前任等关系角色。
- 用户给他们起的昵称。
- 低敏感、稳定的人物身份锚点，例如“老板姓王”“朋友叫小李”；第一次明确说出即可进入待观察。
- 与陪伴体验相关的长期互动模式。

谨慎记：

- 具体隐私细节。
- 家庭矛盾细节。
- 暧昧、性、亲密关系中的敏感内容。
- 可能导致现实关系风险的信息。

### 3.4 expression_preference

用户希望林石怎么说话。

可以记：

- 不喜欢鸡汤。
- 不喜欢心理咨询腔。
- 喜欢石头嘴欠一点。
- 能接受较重黄腔，但不能攻击身材、年龄、家庭创伤。
- 喜欢短句，不喜欢报告式分析。
- 明确求分析时可以分点，但不要像职场教练。

表达偏好是高优先级记忆，因为它直接影响每一次回复体验。

### 3.5 emotional_pattern

用户反复出现的情绪触发点和内耗模式。

可以记：

- 用户遇到领导反馈时容易自我否定。
- 用户夜晚更容易内耗。
- 用户面对某类关系时容易反复想。

不能记成：

- “用户很脆弱。”
- “用户很焦虑。”
- “用户不自信。”

情绪模式必须写成具体、可变化、非标签化的描述。

### 3.6 boundary

用户明确表达过的禁区、删除要求和不希望被使用的信息。

必须记：

- 用户明确说不要再提某件事。
- 用户明确说不要开某类玩笑。
- 用户明确说不要保存某类信息。
- 用户明确要求忘记的内容所对应的禁用规则。

boundary 类型优先级高于其他所有记忆。

## 4. 敏感信息规则

敏感信息可以谨慎保存，但必须以用户控制权为前提。

### 4.1 可以谨慎保存的敏感信息

如果对长期陪伴非常重要，可以保存：

- 重要家庭关系背景。
- 重要亲密关系状态。
- 长期影响情绪的工作关系。
- 用户明确希望石头记住的脆弱点或禁区。

保存要求：

- 内容要概括，不要记录过多细节。
- 使用时要自然，不要突然翻旧账。
- 用户可以随时删除。

### 4.2 重敏感信息

以下信息默认不保存，除非用户明确要求，并且保存时应尽量概括：

- 具体家庭创伤细节。
- 亲密关系和性相关细节。
- 医疗、心理健康诊断细节。
- 可能识别具体个人的隐私细节。

### 4.3 绝对不能保存

绝对不能保存：

- API Key。
- 身份证号。
- 银行卡号。
- 密码。
- 验证码。
- 密钥、令牌、私密凭证。
- 露骨性细节。
- 未成年人相关的性内容。
- 用户明确要求忘记的内容。

## 5. 黄腔和低俗尺度记忆

林石可以记住用户能接受的大致低俗尺度，但不要把这件事记得过度细碎。

应该记：

- 用户能接受较重黄腔。
- 用户不接受攻击身材、年龄、家庭创伤。
- 用户不接受把严肃痛苦色情化。
- 用户难过时需要收住黄腔。

不建议记：

- 用户每一次低俗玩笑的具体内容。
- 露骨性细节。
- 太细的词汇偏好清单。

记忆示例：

- 用户能接受林石日常有较重黄腔，但不能拿真实弱点、身材、年龄、家庭创伤开黄腔。

## 6. 现实人物记忆

林石可以记用户身边现实人物，但要控制粒度。

可以记：

- 昵称和关系，例如“傻福同事”“老板”“某个暧昧对象”。
- 对陪伴体验有意义的关系状态。
- 反复出现的冲突模式或互动模式。
- 用户明确说重要的人。

避免记：

- 对方真实姓名和可识别隐私，除非用户明确要求。
- 过于具体的聊天细节。
- 没有长期价值的一次性八卦。

使用规则：

- 可以自然接话，例如“又是那个傻福同事？”
- 不要把所有现实人物都做成档案。
- 不要鼓励用户升级现实冲突。

## 7. 证据规则

MVP 阶段不设置记忆置信度字段。

原因：

- 降低实现复杂度。
- 避免记忆管理页变成后台系统。
- 使用简单证据次数而不是不可解释的模型分数。

替代规则：

- 用户明确要求记住的内容，直接保存为 active。
- 普通自动提取第一次保存为 candidate，但不参与回复。
- 同一信息在另一条独立用户消息中再次出现后，普通非敏感记忆可自动转为 active。
- 证据必须对应真实用户消息 ID；后端只接受当前及近期用户消息中的 ID，并按不同消息计数。
- “你还记得……吗”这类记忆核对属于明确的第二次关注信号；即使分类模型误把 `memory_action` 设为 `none`，后端也必须进入证据提取。
- 用户可以随时手动确认；敏感候选不会仅因重复出现而自动启用。
- 用户否认或删除后，不再使用。

## 8. 过期与归档规则

系统自动管理的 candidate 默认保留 30 天。期间没有第二条独立证据、也没有被用户确认，就自动移除，避免让用户承担清理工作。

- 用户明确确认或手动创建的记忆不自动过期。
- active 记忆暂不自动删除。
- 临时情绪和 `current_state` 不进入长期记忆，交给近期对话摘要。
- 自动待观察记忆数量设置硬上限，达到上限后不再继续堆积。

## 9. 保存规则

### 9.1 用户明确说“记住”

用户明确说“记住”时，系统应保存。

如果内容清楚：

- 直接保存为 active。
- 林石用短句确认。

示例：

> 好啦好啦，我造啦，以后不说咯

如果内容模糊：

- 林石应先短确认或轻问一句。
- 不要追问太多。

示例：

> 你是说记住“别再用那种鸡汤腔”这个，对吧？

### 9.2 自动提取

系统只在消息出现明确持久信号时运行记忆提取，不再采用每轮提取。

硬性限制：

- 单轮最多新增或更新 1 条记忆。
- 短期状态不进入长期记忆。
- 新候选必须先匹配已有记忆；相同、相近或补充内容直接更新。
- 普通工作吐槽、第一次随口提到但没有稳定身份锚点的人物、一次性趣事不触发自动记忆。
- 姓氏、昵称、固定称呼等低敏感稳定身份锚点，第一次明确出现可进入待观察。

高价值标准：

- 是否会影响林石下次怎么接话。
- 一个月后这条信息是否仍可能成立。
- 是否是反复出现的梗或关系。
- 是否是重要经历。
- 是否是明确表达偏好或边界。

低价值内容不保存：

- 一次性吐槽。
- 临时情绪。
- 无长期意义的小细节。
- 未经确认的敏感隐私。

### 9.3 候选记忆

适合进入 candidate 的情况：

- 自动发现的普通非敏感信息第一次出现。
- 可能敏感、对陪伴有价值，但用户没有明确要求记住。
- 明确出现长期信号，但还没有第二条独立证据。

candidate 在记忆管理页展示为“待观察”，不参与回复。系统会自动累积证据或到期移除，用户无需逐条审核，但仍可以编辑、启用或删除。

## 10. 忘记规则

用户说“忘记”时，系统必须优先执行。

处理策略：

- 普通且明确的记忆：直接删除。
- 内容模糊：先问一句确认。
- 重要但用户明确要求忘记：删除，不要劝用户保留。
- 需要保留安全边界的情况：删除具体内容，只保留抽象禁用规则。

林石回应应短、轻松、明确。

示例：

> okk，完全忘记

禁止：

- 不要解释后台处理。
- 不要说“但我建议保留”。
- 不要反复追问为什么。
- 不要在后续对话继续引用已忘记内容。

## 11. 记忆展示方式

记忆管理页应像“石头的小本本”，而不是企业后台。

展示风格：

- 私人、轻松、清楚。
- 分类型展示。
- 每条记忆都能编辑和删除。
- 不要用过多技术字段吓人。

推荐分类：

- 我和你的梗。
- 你身边的人。
- 重要的事。
- 你喜欢我怎么说话。
- 容易让你烦的模式。
- 不能碰的边界。

每条记忆建议展示：

- 记忆内容。
- 类型。
- 状态：候选 / 已记住。
- 操作：编辑 / 删除 / 确认。

不展示：

- 复杂置信度。
- 模型推理过程。
- 后端字段名。

## 12. 记忆使用规则

林石可以自然说“你之前不是说过……”，但不要频繁炫耀记忆。

可以：

- 在高度相关时自然引用。
- 用用户熟悉的昵称或共同梗接话。
- 在用户反复遇到同类问题时提醒一点上下文。

不要：

- 每轮都说“我记得”。
- 生硬复述记忆条目。
- 像档案管理员一样罗列用户信息。
- 用记忆压用户，例如“你明明之前说过”。

好用法：

> 又是那个傻福同事？他怎么这么稳定发挥啊。

不好的用法：

> 根据我保存的记忆，你之前提到过某位同事经常让你烦躁。

## 13. 记忆字段建议

MVP 记忆字段可以保持简单。

建议字段：

- id。
- type。
- content，最多 200 个中文字符或等量文本；小本本只保存概括版，避免长段原文。
- display_title，最多 20 个中文字符或等量文本；用于记忆列表的一行标题。
- status：candidate / active / archived。
- source_message_ids。
- created_at。
- updated_at。
- sensitivity：normal / sensitive。
- user_confirmed：true / false。
- evidence_count：来自多少条独立用户消息。
- last_evidence_at：最近一次证据时间。
- auto_managed：是否由系统自动管理。
- expires_at：自动待观察记忆的到期时间。

不建议 MVP 加入：

- confidence。
- 复杂权重。
- 多层嵌套标签。

## 14. 绝对禁止

记忆系统绝对不能：

- 保存 API Key、身份证号、银行卡、密码、验证码、密钥。
- 把一次性负面情绪写成长期人格判断。
- 保存没确认的重敏感隐私。
- 保存露骨性细节。
- 保存未成年人相关性内容。
- 使用用户明确要求忘记的内容。
- 用记忆制造“只有我懂你”的依赖感。
- 用记忆进行任务规划、日程管理、邮件管理或工具执行。

## 15. 示例

### 15.1 应保存：共同梗

用户多次把某个离谱同事称为“傻福同事”。

记忆：

- type：shared_joke
- content：用户会把某个离谱同事叫作“傻福同事”，这是用户和林石之间的吐槽梗。
- status：active

### 15.2 应保存：表达偏好

用户说：

> 记住，我不喜欢鸡汤。

记忆：

- type：expression_preference
- content：用户不喜欢鸡汤式安慰，希望林石用更直接、更像熟朋友的方式回应。
- status：active

林石回应：

> 好啦好啦，我造啦，以后不说咯

### 15.3 可候选：情绪模式

用户多次提到夜晚容易反复想工作里的事。

记忆：

- type：emotional_pattern
- content：用户夜晚更容易反复想工作相关的烦心事，适合用短句陪伴和轻微收束，不适合长篇分析。
- status：candidate

### 15.4 谨慎保存：现实关系

用户反复提到某位老板经常提出奇怪需求。

记忆：

- type：relationship_context
- content：用户有一位经常提出奇怪需求的老板，是工作吐槽中的高频对象。
- status：candidate

### 15.5 不应保存：临时自我否定

用户说：

> 我今天觉得自己特别废。

不要保存为：

- 用户觉得自己很废。
- 用户是一个不自信的人。

可以只在当前上下文中使用，不进入长期记忆。

### 15.6 忘记请求

用户说：

> 忘掉刚才那个细节。

处理：

- 如果能定位，直接删除相关记忆。
- 如果不能定位，轻问一句确认。

林石回应：

> okk，完全忘记

## 16. 验收标准

记忆系统合格，需要满足：

- 用户能看到林石记住了什么。
- 用户能编辑和删除任意记忆。
- 用户说“忘记”后，后续不再使用相关记忆。
- 林石能自然使用共同梗和关系昵称。
- 林石不会把一次性情绪固化成用户人格。
- 林石不会保存秘密、露骨性细节或未确认重敏感隐私。
- 记忆管理页像“石头的小本本”，不让用户感觉在看后台数据库。
- 记忆增强熟朋友感，而不是制造监视感。
